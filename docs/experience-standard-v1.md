# 《尘缘问道 · 剑阵万象》游戏定位与体验标准 v1

日期：2026-11-25。状态：可用于策划、拆任务和样片制作的初版；尚未经过品质样片验证，不代表游戏已达标。

配套文档：[现状差距清单](quality-gap-audit-20261125.md) · [首个品质验证版本任务表](quality-slice-plan-v1.md)。

## 1. 目的与适用边界

让美术、动作、声音、交互、战斗、成长和叙事使用同一套体验尺度。完成任务不能只以“功能存在、按钮可用、测试通过”为依据，还必须展示玩家实际感受到的变化。

当前工作是编制标准与计划，不授权发布、不表示已实施。本文覆盖全游戏的方向；首轮实施范围由配套任务表限定。既有功能、玩家资产与发布历史须保留。后续功能开发走独立 `codex/` 分支与 PR。

本轮品质计划补充既有 `PROJECT.md`，不改写其历史状态、不沿用其中已过时的机器路径或未经核实的测试结果。当前用户要求与根目录 `AGENTS.md` 优先。旧计划若与新设计冲突，任务实施前记录具体冲突与处理方式，不能静默改变存档或业务规则。

## 2. 定位与体验支柱

建议基线：**以御剑战斗为核心、人物关系驱动旅程的国风章节式动作 RPG；成长带来新的战术选择，场景体现人物生活与事件变化。**

该定位是依据现有 2.5D 游戏与本次讨论提出的工作假设，尚未构成用户对具体画风、预算或机制的最终选择。先用实际尺寸的目标画面、动作样片与小战斗验证；大批量资产制作在样片评审后进行。

| 支柱 | 玩家应该获得的体验 | 制作取舍 |
|---|---|---|
| 剑有分量 | 看得懂起手、接触、破绽，操作结果可信 | 动作与判定先成立，再加粒子、震屏和文字 |
| 人在世界里 | 人物有生活位置与行动目的，事件能改变其状态 | 人物站位和行为优先于新增功能入口 |
| 修行有选择 | 能说明为何选择某种技能或成长路线 | 横向战术差异优先于重复的百分比加成 |
| 旅程有节奏 | 紧张之后有缓冲，奖励之后有试用机会 | 战斗、交谈、整备和探索交替，避免连续弹窗打断 |

### 参考作品的使用方式

梦幻西游参考视觉规则的稳定性与成长联系；古剑奇谭参考器物、建筑和人物共同构成世界；仙剑奇侠传参考人物关系与旅途情绪。制作参考板时必须标明具体作品、场景、借鉴点和不采用的部分，不能用“像某系列”代替规格，也不能直接挪用其资产。

### 建议的视觉方向

延续固定斜俯视的 2.5D 绘景，采用克制的国风绘画质感。场景承担环境氛围，角色轮廓承担行动辨识；常态光效低于关键招式。雨中破庙与温暖洞府可以有不同情绪，但必须共用人物比例、材质表达、镜头和接地规则。

不预先指定全部色值、角色头身比、动画帧数或引擎。这些参数必须在 1440×900 的实际画面与动作样片中验证后登记，避免文字标准与最终效果脱节。

## 3. 标准的状态与验收规则

- **硬约束**：存档、主动选择、键鼠、素材权利与交付真实性；不通过即不得发布。
- **品质标准**：本轮样片必须逐项判断通过、未通过或未验证。未验证不能计为通过。
- **试行数值**：本文给出的字号、时长、性能等目标先用于样片；调整时记录测量条件、理由和新值，不为迁就某次结果而无记录地降低标准。

每份证据必须标明版本或文件校验值、日期、浏览器、视口、输入路径、前置状态及是否使用测试数据。截图证明构图与静态状态；录像证明动作、节奏与交互；音频试听证明听觉；自动化证明限定场景下的行为。它们不能互相替代。

## 4. 美术与空间

| 编号 | 标准与制作要求 | 验收方式 |
|---|---|---|
| ART-01 | 一套比例、镜头与材质规则。参考板登记人物头身比、俯视角、角色/建筑尺度、轮廓锐度、主色/强调色和系统字体层级。跨场景不能各自重设规则 | 破庙、洞府与战斗界面三张同尺寸画面对照；说明差异来自环境而非素材制作不一致 |
| ART-02 | 对象落在空间里。脚底锚点、接触阴影、光源方向、前后遮挡、碰撞边界与地面透视一致；人物不因移动或换动作突然改变大小 | 角色沿前后左右路径移动，经过柱子/栏杆等遮挡物；录像检查脚底漂移、穿插和阴影脱节 |
| ART-03 | 人物与设施按生活和使用关系布置。普通 NPC 不统一摆上展示底座；物件位置与用途相符 | 洞府路线图解释每处位置用途；试玩者无需先读标签，也能大致辨认休息、制作与出行区域 |
| ART-04 | 战斗视觉有主次：危险动作和玩家行动最清楚，环境不争夺注意力。常态、强化、关键爆发有明确强度递进 | 普攻、破势、大招三段录像对照；关闭非必要文字仍能辨认敌人和威胁方向 |
| ART-05 | 资产有制作与来源记录。登记作者/工具、许可依据、源文件、导出文件、SHA-256、实际使用位置；保留制作素材，使用系统字体 | 更新美术清单并核验文件；未知来源列为待核实，不能以“已有资产”推定许可；不提交字体、凭据或玩家存档 |

## 5. 动作与声音

| 编号 | 标准与制作要求 | 验收方式 |
|---|---|---|
| MOT-01 | 角色至少具备待机、移动、攻击起手/命中/收招、受击、闪避、倒地状态。整体平移、翻转和倾斜可辅助表现，不能承担全部身体动作 | 主角与一种敌人逐状态录像；正常速度看重心和节奏，慢放检查动作衔接、脚底与接触点 |
| MOT-02 | 动作、攻击判定与音效同步。预警早于伤害，命中与挥空反馈不同，受击方向可辨认；取消窗口与无敌时段有明确设计 | 记录至少 10 次命中/挥空及闪避/受击对照，核对逻辑事件与可见动作；不以伤害数字代替动作证据 |
| AUD-01 | 雨、脚步、衣料、剑刃、受击、界面与音乐承担不同信息；持续环境声不掩盖危险提示。材质和空间变化应有对应声音 | 戴耳机与普通扬声器分别试听并记录；先测正常混音，再分轨定位问题。尚未试听不得评价音质 |
| AUD-02 | 音频由玩家操作激活；音乐与音效可独立调节或静音，偏好可保持。重要信息有视觉对应；降低动态效果设置能抑制震屏与闪烁 | 首次进入、切换场景、静音后刷新、降低动态效果分别验证；不得要求玩家依赖声音或颜色单独判断危险 |

## 6. 交互与信息

| 编号 | 标准与制作要求 | 验收方式 |
|---|---|---|
| UX-01 | 同类操作使用一致的键鼠规则。提示与实际绑定一致；输入框不触发战斗快捷键；弹窗有焦点管理，关闭后回到合理位置；非破坏性退出有明确路径 | 主路径用鼠标与键盘各走一次；检查 Tab、Shift+Tab、Escape、输入框及焦点返回；不覆盖浏览器正常焦点导航 |
| UX-02 | 玩家主动选择才推进剧情、消费或领取。消费前说明成本、所得与不可逆后果；操作后给出可辨认结果；失败不显示成功 | 正常、余额不足、重复输入、取消及写入失败场景验证；剧情展示与剧情确认分开，不能因打开面板就扣费或领奖 |
| UX-03 | 战斗信息分层：即时危险优先，操作提示其次，成就和非紧急奖励延后。首轮目标为同时最多 1 条非紧急浮层；关键区域不得被连续文字覆盖 | 记录一场完整战斗和结算，核对提示时间线；状态不丢失，延后提醒仍有可达的查看/领取入口 |
| UX-04 | 1440×900、100% 缩放下主要正文建议不小于 16 px，辅助文字不小于 14 px；普通文字对比度目标 4.5:1，大字 3:1；键盘焦点可见 | 检查实际渲染字号与对比度，包括不同背景、禁用和悬停状态；Canvas 文本同样检查；截图不能代替完整可访问性验证 |
| UX-05 | 教程按当前情境给出一个可立即完成的动作；安全区不继续要求战斗操作，离开后能恢复正确步骤；首次阅读不能无提示地暴露在致命威胁中 | 新开局、战斗中撤退、再进入与刷新后续玩；记录提示、敌人状态和教程步骤是否同步 |

## 7. 战斗、成长与经济

| 编号 | 标准与制作要求 | 验收方式 |
|---|---|---|
| PLAY-01 | 每种主要敌人至少要求一种有区别的应对。动作体现蓄力、攻击、失手或恢复；精英不只增加血量 | 普通敌人与精英分别演示成功应对和错误应对；首次见招后的第二次尝试，玩家能够提出明确调整 |
| PLAY-02 | 每个核心技能说明适用情境、成本/风险和与其他技能的关系。按住一个按钮不能成为所有设计情境中的稳定最优策略 | 在相同装备、固定遭遇下比较无判断输入与按机制处理；记录耗时、受伤、资源消耗，人工解释差异，避免用单一分数判定 |
| PLAY-03 | 首次成长提供至少 2 个可理解的战术方向，并安排试用。奖励可以增强数值，但核心选择应改变打断、范围、节奏或资源使用之一 | 同一遭遇分别试用两个方向；玩家能用自己的话说明区别；每个方向至少有一个适合它的情境 |
| PLAY-04 | 节奏包含交锋、缓冲、整备与再挑战。普通战、精英战、失败重试的耗时和资源成本先测基线再调；失败应提示可执行改进 | 记录完整流程，不用无敌或跳关代替首次体验；区分读剧情、探索、战斗和停留时间，不因玩家读得慢判定失败 |
| PLAY-05 | 奖励与投入对应；重复进入、取消、刷新和重复领取不能刷出额外资产；消费和领取保持显式 | 成长与结算路径检查资产前后值、重复操作和存档恢复；不把自动显示结果误当作授权领取 |

## 8. 世界、人物与叙事

| 编号 | 标准与制作要求 | 验收方式 |
|---|---|---|
| NAR-01 | 事件具备可见的前因、现场状态与后果。遇险、抵抗、获救、休整的姿态/站位与对话一致 | 对比救人前、救人后、返回洞府三个状态；关键变化至少同时通过场景/人物表现和可查询记录中的一种持久形式呈现 |
| NAR-02 | 主线让玩家理解当前目标、理由和下一步。术语采用同一词表；角色对白体现身份与处境，避免所有人都像功能说明 | 未参与开发者完成后复述“为何救人、接下来去哪”；检查可见界面的章节单位、人物称谓和关键技能名 |
| NAR-03 | 玩家选择必须有承诺范围内的后果；不虚假宣传分支。至少有一次后续对话、场景或战术条件兑现 | 选择后、刷新后和返回场景后检查对应结果；将承诺与实现逐项对照，纯态度表达须如实说明 |

## 9. 技术、兼容与交付

| 编号 | 标准与制作要求 | 验收方式 |
|---|---|---|
| TECH-01 | 实际入口 `web/public/playable-v2.html`；直接打开及静态 HTTP 均验证，1440×900 桌面 Chromium，测试上下文与玩家数据隔离 | 保存入口方式、浏览器版本、操作路径及错误日志；正式路径使用真实键鼠输入，测试注入仅作注明的前置搭建 |
| TECH-02 | 存档读取失败明确显示并保留原文；写入失败不宣称成功；多标签页竞争可识别；迁移不删除原数据或使既有进度倒退 | 涉及存档变更必测开局、合成旧档续玩、刷新、写入失败、多标签页竞争；每案用独立上下文，竞争案在同一专用上下文开两页共享存储 |
| TECH-03 | 性能目标先登记测试机器与基线。首轮暂以典型战斗稳定接近 60 FPS、帧间隔 p95 ≤25 ms、无可复现的交互卡顿为目标 | 同一机器、浏览器、装备和遭遇测至少 60 秒，区分预热与稳定段；提交原始指标、采样方法及资源体积差异；本轮尚无测量结果 |
| TECH-04 | 真实验证与交付可追溯。功能分支/PR保留历史；功能、安全、视觉、声音与试玩分别报告；未测明确列出 | 核对当前实际存在的脚本再执行；失败记录原因，不通过删断言伪造通过；发布包素材清单与实际文件一致 |

## 10. 样片品质闸门

所有硬约束通过后，分别检查：视觉融合、动作反馈、战斗决策、人物与世界、交互可读性、声音节奏。

每个维度使用 0–3 级：0=缺失或明显错误；1=可运行但明显破坏体验；2=达到本文具体标准；3=稳定且有辨识度。每项必须附证据与理由，未验证另记。样片要求每个维度至少 2 级，不允许用平均分抵消短板。评分是评审记录，不能当作客观测量替代具体条款。

招募 3–5 名未参与开发的试玩者，记录人数、游戏经验和观察过程。目标是至少 80% 无开发者口头指导完成主要流程，并能说明事件动机、一次战斗调整和成长选择差异；小样本仅作方向判断，不宣称统计显著。若未达到，记录阻碍发生的位置并修复后复测。

## 11. 标准维护

每个任务引用条款编号，不复制一套不同规则。对颜色、动作时长、资源预算等试行参数的调整，记录“旧值 → 新值、原因、证据、影响范围”。新的核心方向改变需由产品负责人确认后更新版本；常规实现选择由实施者在既有授权内推进。

验收记录模板：条款编号｜版本/校验值｜场景与前置条件｜输入步骤｜期望｜实际｜证据路径｜通过/未通过/未验证｜后续责任。

变更记录：2026-11-25，建立 v1 工作基线；目标画面、动作样片、声音试听、性能基线与外部试玩均待后续执行。
