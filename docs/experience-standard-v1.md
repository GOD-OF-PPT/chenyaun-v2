## 1. 目的与适用边界

让美术、动作、声音、交互、战斗、成长和叙事使用同一套体验尺度。完成任务不能只以“功能存在、按钮可用、测试通过”为依据，还必须展示玩家实际感受到的变化。

当前工作是编制标准与计划，不授权发布、不表示已实施。本文覆盖全游戏的方向；首轮实施范围由配套任务表限定。既有功能、玩家资产与发布历史须保留。后续功能开发走独立 `codex/` 分支与 PR。

本轮品质计划补充既有 `PROJECT.md`，不改写其历史状态、不沿用其中已过时的机器路径或未经核实的测试结果。当前用户要求与根目录 `AGENTS.md` 优先。旧计划若与新设计冲突，任务实施前记录具体冲突与处理方式，不能静默改变存档或业务规则。

## 2. 定位与体验支柱

建议基线：**以御剑战斗为核心、人物关系驱动旅程的国风章节式动作 RPG；成长带来新的战术选择，场景体现人物生活与事件变化。**

该定位是依据现有 2.5D 游戏与本次讨论提出的工作假设，尚未构成用户对具体画风、预算或机制的最终选择。先用实际尺寸的目标画面、动作样片与小战斗验证；大批量资产制作在样片评审后进行。

| 支柱 | 玩家应该获得的体验 | 制作取舍 |
|---|---|---|
| 剑有分量 | 看得懂起手、接触、破绽，操作结果可信 | 动作与判定先成立，再加粒子、震屏和文字 |
| 人在世界里 | 人物有生活位置与行动目的，事件能改变其状态 | 人物站位和行为优先于新增功能入口 |
| 修行有选择 | 能说明为何选择某种技能或成长路线 | 横向战术差异优先于重复的百分比加成 |
| 旅程有节奏 | 紧张之后有缓冲，奖励之后有试用机会 | 战斗、交谈、整备和探索交替，避免连续弹窗打断 |

### 参考作品的使用方式

梦幻西游参考视觉规则的稳定性与成长联系；古剑奇谭参考器物、建筑和人物共同构成世界；仙剑奇侠传参考人物关系与旅途情绪。制作参考板时必须标明具体作品、场景、借鉴点和不采用的部分，不能用“像某系列”代替规格，也不能直接挪用其资产。

### 建议的视觉方向

延续固定斜俯视的 2.5D 绘景，采用克制的国风绘画质感。场景承担环境氛围，角色轮廓承担行动辨识；常态光效低于关键招式。雨中破庙与温暖洞府可以有不同情绪，但必须共用人物比例、材质表达、镜头和接地规则。

不预先指定全部色值、角色头身比、动画帧数或引擎。这些参数必须在 1440×900 的实际画面与动作样片中验证后登记，避免文字标准与最终效果脱节。

### 2.1 首次体验关键时刻（v1.1 新增）

四个支柱首先要在新玩家的前 10 分钟里成立。下表把首段旅程拆成可观察的时刻，每一行都引用已有条款，不新增规则。“现状”一列来自复核证据包（`main @ 86e2dc0`）。

| 时刻 | 玩家应该感受到的 | 主要条款 | 复核现状 |
|---|---|---|---|
| 进入破庙后 0–10 秒 | 看懂“谁有危险、我该打谁”；获得一个可立即执行的操作 | NAR-01、UX-05 | 基本成立：气泡写“妖狼围困 · 道友拔剑助我！”，入道 1/4 给出操作 |
| 第一次危招 | 先看到前摇，再知道可以“一闪”；第一次失误不致死，或者失误后马上知道原因 | MOT-02、UX-05、PLAY-01 | 未达：原地连挥 5.4 s 死亡，一闪在第 2 步才教；死亡复盘清楚 |
| 清场一刻 | 有收束感：浮字散去、雨声回落，然后才是人物对话 | ART-04、UX-03、AUD-01 | 未达：6 类信息同帧出现，浮字冻结在对白背后 |
| 战后交谈与谢礼 | 对话由自己推进；两份谢礼的差异一眼看懂；选择后马上能感受到变化 | UX-02、UX-06、PLAY-03、NAR-03 | 部分：选择与预览已有；Space 会跳过对白；离开后选择台丢失（待实测） |
| 首次回洞府 | 安全、可休整；知道下一步只需做 1–2 件事 | UX-05、ART-03 | 部分：教练条正确；但 13 个以上名牌同时出现，且有战斗浮字残留 |
| 再次出征（青岚荒野） | 能用上刚得到的成长；敌人要求新的应对 | PLAY-01、PLAY-03、PLAY-04 | 未验证 |

验收时，每个时刻至少有一段录像，并使用真实输入。外部试玩中，在这些时刻观察玩家的表情、停顿和操作，作为 §10 品质闸门的补充证据。

## 3. 标准的状态与验收规则

- **硬约束**：存档、主动选择、键鼠、素材权利与交付真实性；不通过即不得发布。
- **品质标准**：本轮样片必须逐项判断通过、未通过或未验证。未验证不能计为通过。
- **试行数值**：本文给出的字号、时长、性能等目标先用于样片；调整时记录测量条件、理由和新值，不为迁就某次结果而无记录地降低标准。

每份证据必须标明版本或文件校验值、日期、浏览器、视口、输入路径、前置状态及是否使用测试数据。截图证明构图与静态状态；录像证明动作、节奏与交互；音频试听证明听觉；自动化证明限定场景下的行为。它们不能互相替代。

## 4. 美术与空间

| 编号 | 标准与制作要求 | 验收方式 |
|---|---|---|
| ART-01 | 一套比例、镜头与材质规则。参考板登记人物头身比、俯视角、角色/建筑尺度、轮廓锐度、主色/强调色和系统字体层级。跨场景不能各自重设规则 | 破庙、洞府与战斗界面三张同尺寸画面对照；说明差异来自环境而非素材制作不一致 |
| ART-02 | 对象落在空间里。脚底锚点、接触阴影、光源方向、前后遮挡、碰撞边界与地面透视一致；人物不因移动或换动作突然改变大小 | 角色沿前后左右路径移动，经过柱子/栏杆等遮挡物；录像检查脚底漂移、穿插和阴影脱节 |
| ART-03 | 人物与设施按生活和使用关系布置。普通 NPC 不统一摆上展示底座；物件位置与用途相符 | 洞府路线图解释每处位置用途；试玩者无需先读标签，也能大致辨认休息、制作与出行区域 |
| ART-04 | 战斗视觉有主次：危险动作和玩家行动最清楚，环境不争夺注意力。常态、强化、关键爆发有明确强度递进 | 普攻、破势、大招三段录像对照；关闭非必要文字仍能辨认敌人和威胁方向 |
| ART-05 | 资产有制作与来源记录。登记作者/工具、许可依据、源文件、导出文件、SHA-256、实际使用位置；保留制作素材，使用系统字体 | 更新美术清单并核验文件；未知来源列为待核实，不能以“已有资产”推定许可；不提交字体、凭据或玩家存档 |

**复核补充（v1.1）**：

- **美术清单流程**：`docs/art-manifest.md` 由 `scripts/art-manifest.mjs` 自动生成，文件头写明不得手改。新增或修改美术时：
  1. 运行时素材放在 `src/assets/runtime/`（由构建内联到发行包），制作源和可编辑文件放在 `web/public/art/<version>/`；
  2. 在 `scripts/art-manifest.mjs` 的 `PROVENANCE_OVERRIDES` 中登记来源、许可与备注；
  3. 依次运行 `npm run build`、`npm run art:manifest`、`npm run art:manifest:check`（清单扫描的是构建后的发行包，所以先构建）。
- **历史欠账**：现有 115 张内联素材整批导入于 `5699ee8`，作者和许可多数未记录，ART-05 验收时应单列为“待核实”。
- **评审截图**：截图等评审证据不属于游戏素材，放在 `docs/analysis/validation/<轮次>/`，并登记校验值，不进入美术清单。
- **人物与场景的可读性**：按 `docs/analysis/producer-review.md` 的立场，人物与场景以轮廓、遮挡和危险识别验收，不对整个人物套用 4.5:1 对比度门槛。

## 5. 动作与声音

| 编号 | 标准与制作要求 | 验收方式 |
|---|---|---|
| MOT-01 | 角色至少具备待机、移动、攻击起手/命中/收招、受击、闪避、倒地状态。整体平移、翻转和倾斜可辅助表现，不能承担全部身体动作 | 主角与一种敌人逐状态录像；正常速度看重心和节奏，慢放检查动作衔接、脚底与接触点 |
| MOT-02 | 动作、攻击判定与音效同步。预警早于伤害，命中与挥空反馈不同，受击方向可辨认；取消窗口与无敌时段有明确设计 | 记录至少 10 次命中/挥空及闪避/受击对照，核对逻辑事件与可见动作；不以伤害数字代替动作证据 |
| AUD-01 | 雨、脚步、衣料、剑刃、受击、界面与音乐承担不同信息；持续环境声不掩盖危险提示。材质和空间变化应有对应声音 | 戴耳机与普通扬声器分别试听并记录；先测正常混音，再分轨定位问题。尚未试听不得评价音质 |
| AUD-02 | 音频由玩家操作激活；音乐与音效可独立调节或静音，偏好可保持。重要信息有视觉对应；降低动态效果设置能抑制震屏与闪烁 | 首次进入、切换场景、静音后刷新、降低动态效果分别验证；不得要求玩家依赖声音或颜色单独判断危险 |

**复核补充（v1.1，MOT-01/02）**：主角已有程序姿态状态机（`src/runtime/renderer.js:47-125`：idle/run/light1-4/heavy/dodge/hit/knockdown/meditate）、脚底锚点、接地阴影、残影、顿帧和震屏，但所有状态都由同一张立绘的位移、挤压和倾斜表现，**剪影不变**。敌人前摇只有倾角和小幅抬高。MOT-01 的实施应保留现有状态名、锚点与判定时序，只替换或补充各状态的关键姿势图；不要另建一套状态机，以免破坏已验证的输入与判定。

**复核补充（v1.1）**：当前全部声音由 Web Audio 实时合成（无音频文件），首次指针操作后才解锁，已满足“由玩家操作激活”。AUD-02 的未达项已在代码中证实：

- “战斗音效”按钮的提示写“开关剑鸣鼓点等战斗音效”，实际是**总静音**；
- 五轨混音按乐器（古琴/编钟/战鼓/刀剑/混响）划分，不是按“音乐 / 音效 / 界面”；古琴轨同时用于 BGM 和界面提示音；
- 静音与 BGM 开关**不持久化**，只有混音值保存在 `chenyuan_stems_v22`。

建议提供“总音量 / 音乐 / 音效 / 界面”四个控制并持久化，五轨混音保留为高级选项。减弱动效已有 a11y 设置（震屏、顿帧 0–150%，`reducedMotion` 跟随系统偏好）；验收时另需确认全屏闪光和反相帧在减弱动效下关闭，因为目前没有独立的闪光强度设置。

## 6. 交互与信息

| 编号 | 标准与制作要求 | 验收方式 |
|---|---|---|
| UX-01 | 同类操作使用一致的键鼠规则。提示与实际绑定一致；输入框不触发战斗快捷键；弹窗有焦点管理，关闭后回到合理位置；非破坏性退出有明确路径 | 主路径用鼠标与键盘各走一次；检查 Tab、Shift+Tab、Escape、输入框及焦点返回；不覆盖浏览器正常焦点导航 |
| UX-02 | 玩家主动选择才推进剧情、消费或领取。消费前说明成本、所得与不可逆后果；操作后给出可辨认结果；失败不显示成功 | 正常、余额不足、重复输入、取消及写入失败场景验证；剧情展示与剧情确认分开，不能因打开面板就扣费或领奖 |
| UX-03 | 战斗信息分层：即时危险优先，操作提示其次，成就和非紧急奖励延后。首轮目标为同时最多 1 条非紧急浮层；关键区域不得被连续文字覆盖 | 记录一场完整战斗和结算，核对提示时间线；状态不丢失，延后提醒仍有可达的查看/领取入口 |
| UX-04 | 1440×900、100% 缩放下主要正文建议不小于 16 px，辅助文字不小于 14 px；普通文字对比度目标 4.5:1，大字 3:1；键盘焦点可见 | 检查实际渲染字号与对比度，包括不同背景、禁用和悬停状态；Canvas 文本同样检查；截图不能代替完整可访问性验证 |
| UX-05 | 教程按当前情境给出一个可立即完成的动作；安全区不继续要求战斗操作，离开后能恢复正确步骤；首次阅读不能无提示地暴露在致命威胁中 | 新开局、战斗中撤退、再进入与刷新后续玩；记录提示、敌人状态和教程步骤是否同步 |
| UX-06（v1.1 新增） | 战斗输入与叙事确认隔离。战斗键（左键、右键、Space、WASD、Q、B）在战斗结束、对白或选择出现后的短时间内，不得推进对白、选择谢礼或确认消费。试行规则：①新对白或选择出现后 400 ms 内忽略推进输入（v1.2 决策 D-08，原试行值 0.6 s）；②战斗中已按下的键必须松开、再按下才算确认；③Space 作为“一闪”时不同时承担对白确认，对白只能用 Enter 或点击“继续”推进。E 已绑定“本命法宝剑域”，不能用作确认键；新增确认键前需对照 `flagship-systems.js` 的键位表 | 清场瞬间连按 Space、E、左键各 10 次（Enter 在保护期内连按）：对白不跳句，选择不被触发，消费不发生；键盘玩家仍可在保护期结束后用 Enter 或 Tab 加 Enter 推进；记录焦点位置与保护期时长 |

**复核补充（v1.1）**：

- **UX-03 跨通道仲裁**：当前已有 toast 分级、战斗延后（`combatNoticeLevel` 默认 lite，toast 同时最多 2 条）和横幅浮字上限 3 条。但对白栏、选择卡、Boss 横幅、教练条、解锁卡、评级面板各自独立绘制，首战清场瞬间可同帧出现 6 类信息（复核 R02）。条款中的“非紧急浮层”统计范围应覆盖以上**全部通道**。另外增加两条规则：
  - **清场静默窗**：最后一个敌人倒下后，先让战斗浮字淡出（建议 ≤ 0.8 s），再弹出对白和选择。
  - **场景切换清空**：切换场景时清空战斗浮字，并重置连击面板。
- **UX-04 当前基线**：1440×900 实测，破庙战斗画面有 25 处 10–11 px 文本，洞府有 43 处（复核证据包 `r-capture-log.json`）；Canvas 敌人标签为 10–11.5 px。建议**调整既有字阶 token**，不要另建：`src/styles/main.css:28-33` 已定义 `--fs-xs 11 / sm 12 / md 13 / lg 15 / xl 18 / 2xl 24`（Q2 F14），但仍有大量硬编码的 9–10.5 px 绕过了 token。分三步：①把硬编码字号收归 token；②将 token 整体上调，向“正文 16、辅助 14、键帽/角标最低 12”靠拢；③按“任务追踪 → 技能栏 → 敌人标签 → 洞府名牌”的顺序验收。字号放大后要配合减少同屏文字，不能单纯放大导致遮挡更多。对比度 4.5:1 只针对文字本身，不对人物立绘或装饰套用（与 `producer-review.md` 的立场一致）。
- **UX-05 首个危招**：首战第一次出现危招前摇时，如果玩家还没学过“一闪”，应给出情境提示（短暂慢放或停顿，并显示“空格 · 一闪”），或者首波伤害低于致死线。现状：入道第 1 步只教走位和连挥，第 2 步才教一闪；复核中原地连挥 5.4 s 死亡，致死招式为危招。

## 7. 战斗、成长与经济

| 编号 | 标准与制作要求 | 验收方式 |
|---|---|---|
| PLAY-01 | 每种主要敌人至少要求一种有区别的应对。动作体现蓄力、攻击、失手或恢复；精英不只增加血量 | 普通敌人与精英分别演示成功应对和错误应对；首次见招后的第二次尝试，玩家能够提出明确调整 |
| PLAY-02 | 每个核心技能说明适用情境、成本/风险和与其他技能的关系。按住一个按钮不能成为所有设计情境中的稳定最优策略 | 在相同装备、固定遭遇下比较无判断输入与按机制处理；记录耗时、受伤、资源消耗，人工解释差异，避免用单一分数判定 |
| PLAY-03 | 首次成长提供至少 2 个可理解的战术方向，并安排试用。奖励可以增强数值，但核心选择应改变打断、范围、节奏或资源使用之一 | 同一遭遇分别试用两个方向；玩家能用自己的话说明区别；每个方向至少有一个适合它的情境 |
| PLAY-04 | 节奏包含交锋、缓冲、整备与再挑战。普通战、精英战、失败重试的耗时和资源成本先测基线再调；失败应提示可执行改进 | 记录完整流程，不用无敌或跳关代替首次体验；区分读剧情、探索、战斗和停留时间，不因玩家读得慢判定失败 |
| PLAY-05 | 奖励与投入对应；重复进入、取消、刷新和重复领取不能刷出额外资产；消费和领取保持显式 | 成长与结算路径检查资产前后值、重复操作和存档恢复；不把自动显示结果误当作授权领取 |
| PLAY-06（v1.1 新增） | 评级与即时反馈可信。S/A/B/C 评级和连击称号应反映遭遇难度与机制使用，不能在首次尝试的最简单遭遇中轻易拿到最高级；评级附带的战斗增益（攻速、暴伤、掉宝）计入难度曲线，不能把它当作纯展示 | 固定遭遇下分别记录无判断输入、基础连招、完整机制循环三种打法的评级分布（可用 `eval-combat-matrix`）；首战、首个精英、首个首领各至少 3 次真人录像；检查最高评级首次出现的时间点是否符合设计意图 |

**复核补充（v1.1）**：

- **PLAY-01 与 PLAY-02 已有基础**：现有敌招分为金招识破、红危极限闪避、下段踏剑、擒拿拼刀四类，并有三兵种小队和章节变种（`q6-decisions-and-boundary.md` F34 已列出各首领“Telegraph → Counter → Punish”考题）。`design.md` §4 的 84 组矩阵已经比较 afk / basic_lmb / combo_detonate / full_school_loop 四种打法。验收时先复用这些材料，再补真人录像。
- **PLAY-02 的边界**：Q6 决策 D02 要求保留全部技能槽，D01 规定炼丹、灵宠不设硬门槛。调整技能用途时不得删减槽位，也不得让炼丹、灵宠变成主线前置。
- **PLAY-03 的现状**：首次成长就是玉莲台二选一（青莲灵契 / 惊鸿剑诀）。验收应先评估这组选择是否满足“改变打断、范围、节奏或资源使用之一”，不足再改。

**复核补充（v1.1）**：

- **TECH-01 源码与构建**：`playable-v2.html` 是构建产物。编辑源在 `src/`（`src/runtime` 运行期模块、`src/rules` 与 `src/config` 纯 ESM、`src/styles`、`src/markup`、`src/assets/runtime`），改完执行 `npm run build`，再用 `npm run build:check` 确认逐字节一致。**不得手改发行包**，否则 CI 失败，源码也会与产物分叉。“同一时段只有一个任务修改主游戏文件”的约束应理解为：同一时段只有一个任务修改同一个 `src/runtime/*.js` 模块。

## 10. 样片品质闸门

所有硬约束通过后，分别检查：视觉融合、动作反馈、战斗决策、人物与世界、交互可读性、声音节奏。

每个维度使用 0–3 级：0=缺失或明显错误；1=可运行但明显破坏体验；2=达到本文具体标准；3=稳定且有辨识度。每项必须附证据与理由，未验证另记。样片要求每个维度至少 2 级，不允许用平均分抵消短板。评分是评审记录，不能当作客观测量替代具体条款。

招募 3–5 名未参与开发的试玩者，记录人数、游戏经验和观察过程。目标是至少 80% 无开发者口头指导完成主要流程，并能说明事件动机、一次战斗调整和成长选择差异；小样本仅作方向判断，不宣称统计显著。若未达到，记录阻碍发生的位置并修复后复测。

**复核补充（v1.1）与既有试玩协议的关系**：仓库已有 [`docs/analysis/playtest-protocol-v1.md`](analysis/playtest-protocol-v1.md)，规定 5–8 名新玩家、约 30 分钟、零口头教学，有 M1–M8 指标、5 道访谈题、原始记录表，并可用 `#btn-export-playtest-telemetry` 导出遥测。两者分工如下：

- 样片轮使用 3–5 人做方向判断，沿用该协议的记录表、访谈题和遥测导出，并加上本节的六维评分。
- 发布前的 F29 真人试玩门禁仍按该协议 5–8 人执行。
- 不另起第三套问卷。M1–M8 中与本文条款重叠的指标，直接在验收记录里注明对应条款编号。
