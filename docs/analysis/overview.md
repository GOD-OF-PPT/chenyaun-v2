**1. 总体判断**

项目具备明确题材、基础战斗、修炼渡劫、故人关系和丰富侧边玩法，已经越过“有没有功能”的阶段。当前品质问题集中在四条链路：

1. 战斗行为触发过多通知和选择，反馈竞争发展为遮挡、误触、抢焦点与暂停。
2. 内容入口和成长系统缺乏主次，玩家难以区分“现在必须做”“可以选择做”“以后才会用”。
3. 数值说明、组合收益与实际获得成本没有形成统一可验证的体系。
4. 历史功能交付与动态验收分离，旧测试假设没有及时更新，导致迭代无法依赖完整的可信基线。

下一轮以“前 20～30 分钟完整体验样板”为核心交付：破庙救人 → 初缘选择 → 荒野追猎 → 洞府整备 → 狼王 → 首次渡劫。时长是试验目标，不是当前实测通关时间。先恢复验证能力、修正焦点与待处理收益风险，再治理打断、导航和战斗表现，最后把规范复制到后续卷次。

**4. 对关键证据的解释与修正**

- B 记录的 180 秒内 128～134 条横幅说明特定机器人输入策略下反馈密集，不是所有玩家的固定频率；388/500 次打开设置反映重复输入复现，不是数百名玩家的留存数据。
- B 写“游戏能从头到尾打通”，但其附录明确只自然推进到第一卷星图；本轮不据此认定全流程已通关。
- H 中 M3–M6 为功能与静态检查交付，动态测试延期到 M7；不能改写为这些功能没有实现，也不能按 DONE 直接宣布已验收。
- B 的“缺少 token”应收敛为“已有变量没有覆盖统一设计体系”；C 和源码均确认已有颜色变量、阴影、顿帧和受击闪白。
- B 的“没有设计文档”不能解释为仓库完全无计划：根目录 PROJECT.md 已存在；实际缺的是与当前行为一致、以玩家循环为中心的简洁设计基线。
- C 的 M1-2 失败可由 45% 单击上限解释；P1-1 在开场对白期间未进入有效战斗。它们是已识别的测试假设漂移，不能推导其他失败也只是旧测试。
- 当前本地脚本静态计数为 31 个顶层 runSuite，未找到 R3–R6 套件，`tests/e2e/run.mjs` 不存在；CI 配置确实先校验美术清单，且 E2E 缺失时可跳过。远端运行是否仍失败，本次未查询。
- 美术字节量不是清晰度指标。C 的补充核对显示内联/磁盘灵宠可能具有不同透明通道和内容；资产拆分须以实际运行版本为基准。

**5. 战斗静默方案：采纳方向，补全状态与数据边界**

采用四类通知策略，但为避免与研发优先级 P0/P1 混淆，执行计划命名为 N0–N3：

| 类别 | 包含内容 | 综合处理原则 |
|---|---|---|
| N0 必须立即处理 | 败北、存档冲突/读取失败等关键状态 | 维持明确反馈与必要暂停；去重不能让持续错误消失 |
| N1 需要主动选择 | 背包处置、魂印、神通道果、大限选择等 | 权益先记录；战斗中不自动抢焦点，合适结算窗口或玩家主动打开后逐项处理 |
| N2 信息汇总 | 普通掉落、成就、修为和寿元阈值 | 战中简洁提示，明细进战报，清场汇总 |
| N3 重复反馈 | 连招大字、反复资源不足、重复入道提示 | 去重、限流或降级；危险预警保留独立高优先级 |

首次叙事属于有意设计的流程节点，应在开战前或结算后串行播放，不能让“关键叙事”成为战中任意插入大弹窗的通行证。提示密度的完整/精简/极简只改变信息量，不能恢复不安全的自动选择或遮挡行为。

原提案需补四项保障：

1. **安全不等于敌人数量为零。** 还需考虑敌方投射物、危险区域、即将到来的波次、败北、渡劫与侧边模式结束状态。现有 `isMeditationSafeZone()` 可复用部分判断，但不能直接成为所有模式的最终合同。
2. **调度不能只依赖运行中的战斗帧。** 暂停、关窗、读档、返回洞府和模式结束均应触发重新评估，避免“等待清场弹窗，但暂停使检查永远不执行”。0.8 秒仅作为候选宽限参数。
3. **暂停需要所有权。** 使用按界面实例持有的 token 或等效引用管理；同类窗口同时存在时，简单 `Set('modal')` 仍可能提前释放。焦点由当前最上层合法界面拥有。
4. **延期必须覆盖完整权益生命周期。** 持久化排队项与正在处理项，保持唯一事件/物品 ID，记录确认结果，防止刷新丢失或重复领取。信息战报可以截断，未处理奖励不能因日志长度限制被丢弃。

A 中“靠近道具时 Enter 优先于 HUD”需要收窄：战场拥有焦点时执行道具交互；玩家主动 Tab 到按钮或输入框时保留原生键盘语义。修正错误的焦点返回，不能用全局吞 Enter 掩盖问题。

**6. 分歧与设计决策登记**

以下是方案选择，不是已获准的功能变更。默认保守路径让测试、打断、视觉和首卷打磨能够继续；执行计划用 D01–D08 跟踪依赖这些选择的扩展。

| 决策 | 来源分歧 | 当前计划采用的基线 | 扩展前需要的依据 |
|---|---|---|---|
| D01 核心循环是否强制炼丹/灵宠 | B 倾向每环必需；C 强调选择与代价 | 标明必做/推荐/可选，保持现有可选强渡和辅助系统 | 新手完成率、材料路径与两种渡劫路线成本对比 |
| D02 槽位与系统删减 | B 提议合并攻击体系、R/G、限制高阶技；C 提议两主动加一终极的试验 | 先做按键职责与重叠审计，保留能力和旧档；沙盒比较配置 | 操作负担、流派差异、玩家已解锁内容的迁移方案 |
| D03 卷轴中枢与菜单数量 | B 提议 M/T 合并、三抽屉、固定按钮数；C 强调任务排序 | 统一导航数据和语义，当前主线优先，入口保持可达 | 原型任务查找测试、键鼠与旧入口兼容 |
| D04 第五卷是否新增关卡/Boss | B 要求六卷六关；C 允许旧场景剧情深化 | 先补叙事目标与可感知变化，不新增硬门槛 | 内容成本、自然进阶样本；如收紧终局门槛需兼容旧档 |
| D05 难度缩放与资源/评级合并 | B 提议统一缩放、减少资源评级；C 要求收益预算先行 | 保留现有模式规则，先建立收支和强度矩阵 | 境界成长感、跨模式收益、公平性和旧值转换 |
| D06 源码拆分与调试接口 | H 暂保单文件且不删除旧钩子；B/C 提议模块化 | 独立 HTML 发行不变；先小范围提取配置，旧 V18–V25 接口兼容 | 可重复构建、离线入口、测试与旧档对比；不能直接改名旧接口 |
| D07 双人/天时等开关与误触策略 | B 提议沙盒化、双按菜单键 | 先核对解锁入口一致性和实际强度；保留明确主动暂停菜单 | 不同输入方式试验；不能默认删去同屏玩法或屏蔽用户主动菜单 |
| D08 快捷养成与减负 | 外部建议有长按加速、扫荡；C 限定主动消费 | 单次/明确数量操作及成本预览；维持当前产品定位 | 误操作与资源测试；扫荡、移动端另立产品范围 |

不把“≤10 键、22 个 HUD 按钮、6–8 种资源、每突破最多两键、固定 180ms 转场”等提案自动升级为硬指标。已有验收约束如凡人 HUD 上限，应先统一可见性、情境和计数口径，再判断是否需要设计调整。

**8. 验收口径与范围边界**

发布条件优先采用可观察行为：混战中拾取不会弹普通选择；存档异常立即明确提示；刷新后权益不丢不重；键盘可完成首卷；数值说明符合实效；升级有清楚成本与结果；危险可辨认；两流派存在可理解的取舍。

普通敌人 3～6 秒、精英 12～25 秒、早期首领 45～90 秒、首卷 20～30 分钟，以及 5～8 名新玩家、80% 无讲解完成关键操作，均为候选评测设置。必须绑定配置、版本、输入和样本量，不能作为现版已有成绩。完整主线、音频质量、目标设备性能及晚期自然经济仍缺证据。
