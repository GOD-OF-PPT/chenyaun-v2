## 1. 版本目标与范围

完成一段约 20–30 分钟的首次体验：**进入破庙 → 读懂并处理战斗 → 救下沈清禾 → 主动完成战后交谈 → 返回洞府 → 作出一次成长选择 → 在后续战斗中验证新打法。**

时长为试行目标，排除长时间停留，允许不同玩家阅读与探索速度不同。不能用强制等待、填充战斗或加快对白来机械凑时长。

本版本交付的是后续全游戏制作的品质参考。范围内先完成一个主角、一种普通敌人、一种与其应对不同的精英、一个关键 NPC、破庙和洞府相关区域、两个成长方向，以及配套界面和声音。优先复用现有角色与机制。

范围外：全地图重画、全角色动作重做、完整 3D 迁移、新增大型养成系统、多人系统、商业化、全剧情配音。已有其他系统保持可用，是否简化早期入口由体验调查决定，不删除玩家已获得内容。

不预先承诺“达到商业系列同等体量”。验收针对标准条款与这段实际体验。

## 2. 基线与工作方式

- 当前主工作树有未提交改动，且与远程分叉。实施前核对预期交付版本、现有独立工作树和差异；不自动 reset、覆盖、合并或推送。
- 本轮文档新增到当前仓库 `docs`；功能实现需建立独立 `codex/quality-<topic>` 分支/工作树，并通过 PR 交付。
- 确定基线时记录提交、工作树差异摘要、游戏文件校验值与资产清单。不能从旧提交创建分支后，误以为包含本次评估的未提交内容。
- 当前游戏为大型单文件，实施按依赖顺序推进；同一时段只有一个任务修改主游戏文件。不为本轮品质升级进行无必要的整文件重写或框架迁移。
- 角色动作选择序列帧还是骨骼动画，由样片质量、生产成本和运行效果决定；保持既有玩法状态与存档合同。
- 下列“责任”表示所需职能，不表示已创建团队、分派代理或获得人员预算。

## 4. 可执行任务包

### QV-00 首战快修（v1.1 新增）

- 责任：工程/交互。优先级：P1。依赖：无，可与 QV-01 剩余部分并行。对应：GAP-15/16/20（必做）、GAP-18（提示部分）；UX-06、UX-03、AUD-02、UX-05。
- 背景：复核在当前 main 上实测到几处问题，修复成本低（S 级），都发生在每位新玩家的前 60 秒，而且不依赖美术方向：
  - 战斗键 Space 会推进剧情对白；
  - 战斗浮字在对白期间冻结，并会残留到洞府；
  - 音频偏好刷新后丢失。

  先修这几处，可以让后续样片的“前后对比”建立在干净的基线上。
- 行动：
  1. **输入隔离**：对白或选择出现后约 0.6 s 内忽略推进输入；战斗中按下的键须松开后重新按下才算确认；评估 Space 是否继续兼任对白确认键。
  2. **浮字清理**：进入对白时淡出或清空战斗浮字；切换场景（含 `enterSanctumHub`）时清空 floats，并重置连击面板。
  3. **音频偏好**：分出音乐、音效、界面三个音量（或至少让“战斗音效”名副其实），静音和 BGM 开关持久化到版本化存储键，旧键缺失时取当前默认值。
  4. **首个危招提示**：首次遇到危招前摇时，若还未学过一闪，给一次“空格 · 一闪”的情境提示。数值调整留给 QV-04。
- 交付：`src/runtime` 中的改动加 `npm run build` 的产物；E2E 新增 3 条用例，分别覆盖清场连按、场景切换浮字、静音刷新；修复前后的截图（复用复核证据包的 R02、R03、R05 作为“前”）。
- 验收：
  - 清场瞬间连按 Space、Enter、左键各 10 次，对白不跳句，谢礼不被误选；
  - 回洞府后无战斗浮字；
  - 静音后刷新仍为静音；
  - 键盘玩家在保护期结束后仍能用 Enter 推进；
  - 不改变存档结构（若音频偏好使用新键，需在独立上下文中验证刷新与多标签页）；
  - 全部现有命令（见 QV-10）通过。

### QV-04 建立一场有明确决策的战斗

- 责任：战斗设计/工程。优先级：P1。依赖：QV-03。对应：GAP-08；PLAY-01/02/04、MOT-02。
- 行动：调查现有普攻、剑印、爆剑、闪避/识破的用途；为普通敌人确定“蓄力—攻击—恢复”节奏；精英增加一种不同的应对要求。优先调整既有机制而不是增加新键位。
- 交付：敌人行为与技能用途表、成功/错误应对录像、相同装备下的策略对比记录。
- 验收：玩家能从动作识别至少一次可利用的破绽；按机制处理在耗时、受伤或资源上有可解释优势；错误应对有可理解后果，不能只靠提高血量延长战斗。
- 复核补充（v1.1）：
  - **复用现有材料**：先跑 `node scripts/eval-combat-matrix.mjs --seed <n>`，取出 `mob_pack` 与 `shielded_elite` 两类原型下 afk / basic_lmb / combo_detonate / full_school_loop 四种打法的结果，作为“相同装备下的策略对比”基线；再补真人录像。现有敌招已有金招、红危、下段危、擒拿四类，带符文双编码；精英已有章节变种（金盾、镜反、绕背等），任务是让这些差异**读得出来**，不是新增机制。
  - **复核数据点**：原地按住左键 5.4 s 死亡；移动加连招 3–5 s 清场并得 S 评级。这说明首战的伤害曲线和评级阈值都需要纳入本任务（GAP-17、GAP-18）。

- 复核补充（v1.1）：现有声音全部由 Web Audio 合成（`src/runtime/preamble.js`），已有 BGM 开关、总静音、五轨混音和 PR #26 的分级音效与遥测。偏好分离与持久化已拆到 QV-00 先做（GAP-20）；本任务专注试听、混音和关键事件补声。若改用采样音频，须走 ART-05 的来源与许可登记，并评估发行包体积。

### QV-10 完成整段体验与兼容回归

- 责任：工程/QA。优先级：P0（交付）。依赖：QV-09。对应：GAP-12/13/14；TECH-01/02/03/04、ART-05。
- 行动：直接文件与静态 HTTP 验证真实入口；检查完整旅程、键鼠、失败撤退、重复进入、声音控制、降低动态效果、资源加载及素材清单。执行 QV-01 确认可用且与变更相关的回归，完成项目要求的最终检查。
- 交付：验证矩阵、实际命令及日志、完整流程录像、性能前后对比、已知限制。
- 验收：涉及存档的路径覆盖五场景；多标签页案在专用共享存储上下文中运行；旧档为合成测试数据；读取失败保原文、写入失败不报成功。未测、失败、通过分开记录；发现问题返回对应任务修复并定向复测。
- 复核补充（v1.1）：实际命令为 `npm ci` → `npm run build:check` → `npm run test:unit` → `npm run art:manifest:check` → `npm run test:regression` → `npm run test:e2e`，与 CI `.github/workflows/e2e.yml` 一致。存档五场景已有 E2E Tier 2 覆盖，应在此基础上**新增**本轮改动的断言，不要另写一套。复核时 `E2E-T1-15` 在有负载的全量运行中失败 1 次，单独复跑 3/3 通过；QV-10 需在空载机器或 CI 上确认它是否为对负载敏感的时序问题。证据包放在 `docs/analysis/validation/<轮次>/`。

### QV-11 外部试玩与品质评审

- 责任：产品/QA/试玩参与者。优先级：P1。依赖：QV-10。对应：全部样片标准。
- 行动：安排 3–5 名未参与开发的人试玩；仅给正常游戏入口和基本任务，不在途中讲解设计答案。记录操作困惑、战斗调整、故事复述与成长选择理解。游戏完成后再询问感受。
- 交付：匿名试玩记录、阻碍位置、六维品质评分及证据、修复优先级。没有真实参与者时明确标为待执行，不以代理或脚本替代人类试玩结论。
- 验收：标准文档的硬约束与品质闸门满足；预计 20–30 分钟的流程未靠重复劳动凑时长；不达标项有具体修复与复测结果。参与者尚未安排不应阻止前序制作工作。
- 复核补充（v1.1）：沿用 `docs/analysis/playtest-protocol-v1.md` 的记录表、M1–M8 指标和访谈题，用 `#btn-export-playtest-telemetry` 导出遥测（含 `pedestalChoiceSec` 等字段）作为客观补充。本轮 3–5 人只用于方向判断；发布门禁 F29 仍按协议 5–8 人执行。观察重点放在体验标准 §2.1 的六个关键时刻。

### QV-12 固化标准并安排全游戏推广

- 责任：产品/工程/美术。优先级：P2。依赖：QV-11 通过。对应：全部标准维护。
- 行动：将验证过的色彩、比例、动画规则、战斗节奏、声音和资源预算写回标准；保留实际样片作为参考；重新扫描其余章节，按复用价值和体验影响拆任务。
- 交付：体验标准修订版、可运行品质样片、制作模板、全游戏推广待办、PR/交付说明。
- 验收：每个新增待办都有对应标准、场景、范围和证据要求；没有把样片通过写成全游戏通过；交付如实说明剩余缺口。

## 6. 每项任务的完成定义

必须同时具备：已完成的玩家体验变化、所引用条款的实际证据、涉及数据的兼容说明、必要自动化与真实入口验证、残留问题、可审查差异。只有代码、只有设计图、只有通过数量或只有一句“已优化”均不算完成。

PR 模板：问题与前后行为 → 对应标准/差距/任务编号 → 修改范围与数据影响 → 实际验证及证据 → 未验证范围与后续责任。文档状态、任务状态和实际代码必须一致。
